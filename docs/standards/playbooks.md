# 📖 Playbooks — أنماط العمل في عُدّة

> هذا الملف يُترجم **طلبات المستخدم بصياغة طبيعية** إلى **تسلسل عمل ثابت** للوكيل.
>
> **الفلسفة:** أنت تتكلّم بحرية، الوكيل يستنتج النوع، يطبّق الـ playbook المناسب، مع مرونة في التفاصيل.

---

## 🎯 كيف يستخدم الوكيل هذا الملف

عند تلقّي أي طلب من المستخدم، الوكيل يتبع هذا التسلسل:

1. **تشغيل Session Resume Protocol** أولاً (في [`../../CLAUDE.md`](../../CLAUDE.md))
2. **تحليل الطلب** — ما النوع؟ (جديد / توسيع / إصلاح / محتوى / فحص / refactor / docs / غامض)
3. **اختيار الـ playbook** المطابق من الجدول أدناه
4. **اتباع الخطوات** بمرونة — الذكاء الطبيعي يُغطي التفاصيل غير المذكورة
5. **إذا غامض:** الـ Fallback playbook (اسأل قبل البدء)

## 1. أداة جديدة 🆕

**كلمات تشير له:** "أنشئ"، "بدّي"، "أضف أداة"، "لنبني"، "اعمل أداة"، "new tool"

**التسلسل:**

```
0. Session Resume Protocol (موقع-level — دائماً)
   ↓
1. تحليل الطلب
   - في أي تصنيف؟ (راجع tools.json categoryOrder)
   - مذكورة في 03-ROADMAP.md؟
   - مستوى التعقيد التقديري (موجز / متوسط / عميق)
   ↓
2. قراءة المعايير قبل أي كود
   - standards/tool-template.md (الخطوات الـ8)
   - 02-PRINCIPLES.md (القواعد الإلزامية)
   - standards/mobile-design.md
   - standards/i18n-conventions.md
   - أداة مشابهة (للنمط — مثلاً percentage لحاسبات بسيطة)
   ↓
3. التصميم على الورق + نقاش
   - ما تفعله الأداة بالضبط
   - UI mockup (وصف نصي)
   - حالات حافّة (edge cases)
   - i18n keys مطلوبة
   - disclaimer إن لزم (إسلامي/مالي/طبي)
   📌 انتظر موافقة المستخدم قبل أي كود
   ↓
4. إنشاء workspace (قبل الكود)
   docs/development/{tool}/
   ├── progress.md  (📋 الخطة الأولية)
   ├── memory.md    (قرارات التصميم)
   ├── instructions.md (تعليمات خاصة)
   └── todo.md (المهام الفورية)
   ↓
5. إنشاء spec
   docs/tools/{tool}.spec.md (ما ستكون عليه الأداة نهائياً)
   ↓
6. التنفيذ البرمجي
   - i18n.json (ترجمات ar + en كاملة)
   - tools.json (تسجيل + related)
   - src/tools/{tool}.html (template + scoped CSS + IIFE JS)
   - npm run build بعد كل تعديل كبير
   ↓
7. الفحص الكامل
   standards/testing-checklist.md (13 فئة)
   ↓
8. تحديث temporal markers
   - 04-PROGRESS.md (موقع)
   - development/{tool}/progress.md (أداة)
   - _sessions.md (للجلسة الكبيرة)
   ↓
9. Commits منطقية + Push
   - workspace + spec
   - i18n + tools.json
   - HTML template + كود
   - تحديث markers
   ↓
10. Auto-merge → Deploy → الأداة على udda.tools
```

**نقاط القرار (متى أسأل المستخدم):**
- ✋ بعد الخطوة 3: عرض التصميم → موافقة قبل الكود
- ✋ لو edge case غير مذكور في الطلب الأصلي
- ✋ لو حالة فقهية/طبية تحتاج توضيحاً

## 2. توسيع أداة موجودة ✏️

**كلمات تشير له:** "حدّث"، "طوّر"، "أضف لـ X"، "عدّل في X"، "update"

**التسلسل:**

```
0. Tool-level temporal check
   git log -1 --format='%ai' -- src/tools/{tool}.html
   ↓
1. قراءة workspace الأداة
   - development/{tool}/progress.md (الحالة + الأفكار)
   - development/{tool}/memory.md (القرارات الفقهية/التقنية)
   - development/{tool}/instructions.md (تعليمات خاصة)
   ↓
2. ناقش التغيير
   - هل هو في "📋 Planned"؟ (نُكمل مباشرة)
   - هل هو في "💡 Ideas"؟ (نُحوّل لـ Planned أولاً، نتفق)
   - جديد كلياً؟ (نقاش + موافقة)
   ↓
3. التنفيذ
   - Edit i18n / tools.json / HTML حسب الحاجة
   - npm run build
   ↓
4. الفحص (الفئات ذات الصلة من testing-checklist)
   ↓
5. تحديث
   - development/{tool}/progress.md (نقل البند من Planned → Done)
   - development/{tool}/memory.md (إن اكتُشف قرار جديد)
   - 04-PROGRESS.md temporal marker
   ↓
6. Commit + Push
```

**نقاط القرار:**
- ✋ لو التغيير يلامس فقه/طب → موافقة قبل التنفيذ
- ✋ لو التغيير يكسر backward compatibility → موافقة

## 3. إصلاح bug 🐛

**كلمات تشير له:** "أصلح"، "لا يعمل"، "خطأ"، "broken"، "fix"

**التسلسل:**

```
1. إعادة إنتاج الـ bug (Steps to Reproduce)
   - ما الإدخال الذي يُسبّبه؟
   - ما السلوك الملاحَظ؟
   - ما السلوك المتوقَّع؟
   ↓
2. تحديد السبب الجذري (root cause)
   - لا تُعالج الأعراض فقط
   - افحص الكود في النقطة الفعلية
   ↓
3. الإصلاح + اختبار
   - تعديل الكود
   - اختبار حالة الـ bug + حالات قريبة (لمنع regressions)
   ↓
4. توثيق في memory.md (لمنع التكرار)
   ## ⚠️ حالات حافّة
   - 2026-XX-XX: {وصف الـ bug + السبب الجذري + الإصلاح}
   ↓
5. Commit واحد (fix: ...) + Push
```

**نقاط القرار:**
- ✋ لو الـ bug فقهي/طبي → موافقة + استشارة قبل التغيير
- ✋ لو الإصلاح يتطلب refactor كبير → ناقش الـ trade-off

## 4. مقال مدونة 📝

**كلمات تشير له:** "اكتب مقالاً"، "مقال عن"، "أضف للمدونة"

**التسلسل:**

```
1. اقرأ المعايير
   - standards/blog-template.md
   - standards/content-strategy.md
   - مقالات سابقة عن نفس الموضوع (للنمط + cross-linking)
   ↓
2. ناقش المحتوى
   - الـ topic (أداة من tools.json أو "news")
   - Pillar أم Sub article؟
   - الكلمات المفتاحية المستهدفة
   - الجمهور (مبتدئ/متقدم)
   📌 موافقة على outline قبل الكتابة الكاملة
   ↓
3. الكتابة
   - frontmatter كامل (title, description 150-160 حرف، date، topic، keywords، relatedTool)
   - بنية: مقدمة → CTA1 → أقسام → CTA2 → FAQ → ربط بمواضيع ذات صلة
   - عربي أو إنجليزي (قرار منفصل لكل لغة)
   ↓
4. npm run build (تأكد المقال يُنتج صفحة سليمة + يظهر في sitemap)
   ↓
5. Commit + Push
```

**نقاط القرار:**
- ✋ بعد الخطوة 2 (outline) → موافقة قبل الكتابة الكاملة
- ✋ لو محتوى فقهي/طبي حرج → مراجع موثَّقة في النص

## 5. Refactoring عابر للأدوات 🔧

**كلمات تشير له:** "غيّر في كل الأدوات"، "حدّث X في الكل"، "rename"، "وحّد"

**التسلسل:**

```
1. تحديد النطاق
   - كل الـ11 أداة؟ بعض؟
   - أي ملفات (HTML / CSS / JS / i18n)؟
   ↓
2. تطبيق على أداة واحدة كـ "نموذج"
   - الأبسط من الـ list (مثل percentage)
   - اختبار شامل
   📌 عرض النتيجة قبل التعميم
   ↓
3. تطبيق على البقية (بعد الموافقة)
   - استخدم replace_all بحذر
   - فحص كل أداة بعد التطبيق
   ↓
4. npm run build (شامل)
   ↓
5. Commits متعددة منطقية:
   - أداة-نموذج (commit أول)
   - بقية الأدوات (commit ثانٍ)
   - تحديث docs/standards إن لزم (commit ثالث)
   ↓
6. Push
```

**نقاط القرار:**
- ✋ بعد الخطوة 2 — موافقة قبل التعميم
- ✋ لو رصدت أنماطاً غير متوقَّعة في أداة معينة (قد تحتاج معالجة خاصة)

## 6. تحديث توثيق 📚

**كلمات تشير له:** "حدّث الـ docs"، "عدّل README"، "أضف ملاحظة في X"

**التسلسل:**

```

   ↓
2. اقرأه — فهم السياق الحالي
   ↓
3. التعديل
   ↓
4. تحديث temporal markers لو التعديل يستحق
   ↓
5. Commit + Push
```

**ملاحظات:**
- ❌ لا حاجة لـ `npm run build` (التغيير documentation فقط، لا يلامس src/)
- ✋ لو التعديل يغيّر مبدأ في 02-PRINCIPLES.md أو 05-MEMORY.md → موافقة جوهرية

## 7. فحص توافق 🔍

**كلمات تشير له:** "افحص التوافق"، "session resume"، "check compat"، "هل كل شيء حديث؟"

**التسلسل:**

```
1. Session Resume Protocol كامل
   - Site-level: git log gap, npm outdated, Actions, training cutoff
   - Tool-level (لو محدد): git log per tool, tool-specific concerns
   ↓
2. تقرير شامل بالوضع
   - الفجوات الزمنية
   - تبعيات قديمة
   - أدوات/مراجع محتمل تغيّرها
   - ملاحظات الـ training cutoff
   ↓
3. قائمة مهام مقترحة (للمستخدم لينقلها لـ 06-TODO.md)
   📌 لا تطبيق تلقائي — تنتظر قرار المستخدم
```

**نقاط القرار:** كل قرار تطبيق بعد التقرير ينتظر موافقة المستخدم.

## 9. Autonomous Execution Mode (AEM) 🤖

**ما هو:** نمط يُفعَّل **داخل** playbook آخر (1-6 عادةً)، يُحوّل التنفيذ من "خطوة-سؤال-خطوة-سؤال" إلى **حلقة مستقلة** بعد التخطيط الناضج. الوكيل ينفّذ بنفسه ويتوقّف فقط عند نقاط القرار الحقيقية.

**ليس playbook منفصل** — هو **modifier** للـ playbooks الأخرى. الـ playbook الأم (1، 2، 5...) يُحدّد *ماذا* يُعمل، AEM يُحدّد *كيف* — مستقلاً.

**كلمات تشير له:** "ابدأ التنفيذ"، "نفّذ"، "loop"، "أنجز لوحدك"، "continue autonomously"

---

### شروط التفعيل (يجب أن تتحقّق كلها)

1. ✅ المستخدم قدّم **مدخلاً ناضجاً** (spec، خطة، مواصفات — ليس جملة مبهمة)
2. ✅ تمت **Phase 0** (الاستجواب + البحث + التركيب) → خطة نهائية موافَق عليها
3. ✅ المستخدم أعطى **إذناً صريحاً** بـ AEM
4. ✅ **لا حالات معلَّقة** فقهية/طبية/أمنية بدون قرار

---

### Phase -1: الاستقبال

المستخدم يأتي بمدخل **ناضج** — ليس "أنشئ X" بسيطة، بل:
- spec كامل (~30-100 سطراً)
- خطة مُسبقة (من نقاش/بحث/كتابة شخصية)
- مواصفات تفصيلية أو ملف منفصل

الوكيل **لا يُسلّم** بصحته كاملاً — ينتقل لـ Phase 0.

---

### Phase 0: استجواب + بحث + تركيب ⭐ (الجوهر)

#### أ) استيعاب
- اقرأ المدخل بعناية كاملة
- حدّد النية الجوهرية + التفاصيل + الفجوات الظاهرة

#### ب) بحث في الكود (silent — لا يحتاج إدخال المستخدم)
- **integration:** أدوات مشابهة، patterns للاستفادة، تعارضات محتملة
- **معايير:** هل المدخل يطابق `02-PRINCIPLES`، `mobile-design`، `i18n-conventions`؟
- **CSS:** متغيرات يمكن إعادة استخدامها بدلاً من جديدة
- **i18n:** مفاتيح مكرّرة محتملة، قواعد التسمية
- **scope:** هل التغيير يُضخّم أحداً من الأدوات الـ11 الأخرى؟

#### ج) استجواب — أسئلة استراتيجية للمستخدم
- **3-7 أسئلة فقط** (الجودة قبل الكمّية)
- **ليست للتأكيد** — بل لـ:
  - **الاستزادة:** "ماذا عن X؟"
  - **اتخاذ القرار الصحيح:** "أيهما تُفضّل، Y أم Z؟"
  - **ضمان التكامل:** "هذا قد يتعارض مع W في أداة مجاورة — كيف نحلّه؟"
- **لا تسأل** أسئلة الإجابة عليها واضحة من السياق

#### د) تركيب (synthesis) — خطة الوكيل
يُولّد الوكيل خطة جديدة (ليست خطة المستخدم حرفياً) تُظهر بوضوح:
- ✅ **ما حافظت عليه** من مدخل المستخدم
- 📝 **ما أضفته** من بحثي/معرفتي (مع المبرّر)
- ✏️ **ما عدّلته** (مع المبرّر)
- ⏰ **scope النهائي** (لو اقترحت تقسيمه)
- 📋 **`todo.md`** مُولَّد بـ dependencies + نقاط قرار محددة

#### هـ) عرض الخطة + موافقة
- يُعرض كل ما سبق على المستخدم
- المستخدم يختار: **"نفّذ"** أو **"عدّل X"** أو **"ناقش Y"** أو **"توقّف"**
- لا تنفيذ بدون موافقة صريحة

---

### Phase 1: Execution Loop (الحلقة المستقلة)

```
بعد الموافقة على الخطة، الوكيل يدخل الحلقة:

while (
  مهام متبقية في todo.md         AND
  لم نصل لنقطة قرار 📌           AND
  لا error في build/test          AND
  لا تجاوز budget                AND
  المستخدم لم يقاطع
):
  1. اقرأ todo.md → المهمة التالية
  2. نفّذ
  3. تحقّق:
     - npm run build (إن لزم)
     - فحص الفئات ذات الصلة من testing-checklist
  4. حدّث:
     - todo.md (احذف المنجَز)
     - progress.md (Active → Done)
     - temporal markers (إن كانت آخر مهمة في chunk)
  5. atomic commit (رسالة واضحة بنمط conventional commits)
  6. اعرض ملخصاً قصيراً (سطر-سطرين)
  7. كرّر
```

---

### Phase 2: التقرير الختامي

عند الانتهاء (سواء بـ success أو stop):
- ✅ **ما أُنجز** (مع روابط commits)
- 📋 **ما تبقّى** (إن وُجد)
- ⏸️ **سبب التوقّف**
- 🎯 **الخطوة المقترحة التالية**

---

### نقاط القرار 📌 (يتوقّف الوكيل ويُبلّغ المستخدم)

| السبب | السلوك |
|---|---|
| ✅ كل المهام منجَزة | تقرير ختامي + توقّف نهائي |
| 📌 نقطة قرار محددة في الخطة (مثل: بعد spec، قبل push) | احفظ الحالة + اطلب الموافقة |
| ❌ Error في build/test | احفظ + اطلب التوجيه (لا تتجاوز الأخطاء) |
| 🤔 ambiguity غير متوقَّع (لم يكن في الخطة) | اسأل قبل المضي |
| ⏰ تجاوز budget (commits/tokens/time) | احفظ + قدّم تقريراً جزئياً |
| ⚖️ قرار فقهي/طبي مفاجئ | توقّف فوراً + اطلب الموافقة |
| ✋ المستخدم قاطع | احفظ الحالة فوراً + توقّف |

---

### حدود الأمان (Safety Boundaries)

في AEM، هذه **ممنوعة دائماً** بدون موافقة صريحة جديدة:

| ❌ ممنوع | ✅ مسموح |
|---|---|
| `git push --force` (لأي branch) | `git push` عادي |
| حذف ملفات غير مذكورة في الخطة | إنشاء + تعديل المخطَّط له |
| تعديل في `src/` بدون `npm run build` بعد كل تعديل كبير | تعديل + build verify |
| تجاوز عدد commits المتوقَّع للـ playbook الأم بدون سؤال | الالتزام بحدود الـ playbook |
| تخطّي 📌 نقاط القرار | احترامها كاملاً |
| تعديل `.github/workflows/` بدون موافقة | تعديل في `src/` و `docs/` |
| حذف ملفات في `.git/` أو `node_modules/` | لا |
| مشاركة secrets أو credentials في commits أو chat | لا |
| Push بعد كل commit (ضوضاء) | Push بعد chunk من commits منطقية |

---

### العلاقة بالـ playbooks الأخرى

AEM يُفعَّل **داخل** playbook 1-6 بعد إكمال نقاش التصميم:

| Playbook الأم | مناسبة لـ AEM؟ | ملاحظات |
|---|---|---|
| 1. أداة جديدة | ✅ **ممتازة** | مهام كثيرة معروفة النمط |
| 2. توسيع أداة | ✅ **مناسبة** | مهام جزئية متسلسلة |
| 3. إصلاح bug | ❌ غير مناسبة | المهمة قصيرة، AEM overhead |
| 4. مقال مدونة | 🟡 ممكنة | مهمة واحدة عادة، ليست ضرورية |
| 5. refactoring عابر | ✅ **ممتازة** | sample → approve → propagate تكراري |
| 6. تحديث docs | 🟡 ممكنة لو متعدد الملفات | غالباً صغيرة |
| 7. فحص توافق | ❌ لا | فحص read-only، لا تنفيذ أصلاً |

### مثال كامل (سيناريو حقيقي)

**المستخدم:** يقدّم spec كامل لمحوّل وحدات (~50 سطراً مفصّلة).

**الوكيل (Phase 0):**

أ) استيعاب: قراءة الـ spec
ب) بحث: percentage (نمط instant-result)، kaffara (نمط tabs)، i18n.json (مفاتيح متشابهة)
ج) استجواب:
- "ذكرت 7 وحدات أطوال — هل نضيف الفرسخ والذراع (تاريخية)؟"
- "كيف نتعامل مع حرارة < -273°C (مستحيلة فيزيائياً)؟"
- "هل تريد زر swap (اعكس الوحدتين)؟"
- "scope: الـ spec يذكر تواريخ ومساحات أيضاً. أقترح هذه الجلسة = طول/وزن/حرارة، البقية لاحقاً. موافق؟"

د) تركيب:
```
✅ من مدخلك: 7 طول، 5 وزن، 3 حرارة، instant result
📝 أضيف: zر swap، searchTerms عامي، related في percentage/loan
✏️ أعدّل: tabs بـ flex-wrap (مثل kaffara) بدل dropdown
⏰ scope: المرحلة 1 الآن، تواريخ/مساحات لاحقاً
📋 todo.md: 27 مهمة، 4 commits، 📌 توقّف بعد T02 (spec) و T26 (push)
```

هـ) عرض → موافقة

**الوكيل (Phase 1 — AEM Loop):**
- T01: workspace ← commit 1
- T02: spec ← commit 1 (نفسه)
- 📌 **توقّف:** "spec جاهز — راجعه"

(بعد موافقة):
- T03-T17: i18n + tools.json + HTML + CSS + JS ← commits 2-3
- T18-T22: testing
- T23-T26: temporal markers + final commit

- 📌 **توقّف:** "كل شيء جاهز — قبل push النهائي، راجع على dev"

(بعد موافقة):
- T27: push → auto-merge → deploy
- Phase 2: تقرير ختامي

## Fallback — طلب غامض 🤔

**متى يُستخدم:** لو الطلب لا يطابق أياً مما سبق بوضوح، أو يخلط أنواعاً متعددة (مثل: "أصلح bug في الزكاة وأضف ميزة جديدة لها").

**التسلسل:**

```
1. حدّد الغموض
   - أي playbook(s) قد ينطبق؟
   - ما المعلومات الناقصة؟
   ↓
2. اسأل المستخدم
   - "هذا يبدو {نوع X} — صح؟"
   - "أم تقصد {نوع Y}؟"
   - "هل نقسّمه لـ playbook 3 (bug fix) ثم playbook 2 (extension)؟"
   ↓
3. بعد التوضيح: انتقل للـ playbook المناسب
```
